# Бэкенд: как он устроен сейчас

> Черновой вариант. Документ для того, кто подхватывает бэкенд (Backend — Юдина).

Go 1.23, только стандартная библиотека (`net/http`, `encoding/json`, `archive/zip`…), внешних зависимостей нет.
Один бинарник: держит базу знаний в памяти, отвечает на API и раздаёт собранный фронтенд.

## Структура

```
backend/
├── cmd/server/main.go          точка входа: читает конфиг, грузит базу, собирает зависимости, стартует HTTP
└── internal/
    ├── config/config.go        все настройки из переменных окружения (+ значения по умолчанию)
    ├── kb/kb.go                база знаний: чтение файлов, нарезка на положения, BM25-поиск
    ├── llm/client.go           HTTP-клиент OpenAI-совместимого /chat/completions (DeepSeek)
    ├── assistant/assistant.go  логика ответа: поиск → порог → промпт → LLM → отбор источников
    └── api/api.go              роуты, JSON, обработка ошибок, раздача frontend/dist
```

Зависимости идут строго сверху вниз: `api → assistant → kb, llm`. `assistant` знает только интерфейсы
`kb.Searcher` и `llm.Chatter`, поэтому поиск и модель подменяются без правок логики (так сделаны тесты).

## Что происходит при старте (`main.go`)

1. `config.Load()` — читает env.
2. `kb.Load(KB_DIR)` — рекурсивно обходит папку, читает `.txt`, `.md`, `.docx` (PDF пока пропускается),
   режет на фрагменты и строит BM25-индекс **в памяти**. Пишет в лог: сколько документов и фрагментов.
3. Создаёт `llm.Client` и `assistant.Assistant`, отдаёт их в `api.Server`.
4. Слушает `ADDR` (по умолчанию `:8000`).

База грузится один раз — после добавления документов сервер нужно перезапустить.

## Путь запроса `POST /api/chat`

```
{"question": "...", "history": [{"role":"user|assistant","content":"..."}]}
        │
api.chat ── проверяет JSON (лимит тела 1 МБ) и непустой вопрос → иначе 400
        │
assistant.Answer
  1. строка поиска = 2 последние реплики пользователя из history + вопрос
     (чтобы уточнения вида «а для экспорта?» находили нужное)
  2. kb.Search(строка, TOP_K)
  3. ничего не найдено или лучший score < MIN_SCORE
        → сразу отказ (refused: true), модель НЕ вызывается
  4. собирает промпт:
       system  = SystemPrompt (8 правил: ссылки [n], без выдумок, ошибки в вопросе,
                 редакции документов, законность, защита роли, не по теме)
       history = только user/assistant (поддельные system-сообщения отбрасываются)
       user    = «Фрагменты базы знаний: [1] Документ… Положение… текст … Вопрос: …»
  5. llm.Chat → текст ответа
  6. sources = только те фрагменты, чей номер [n] реально встречается в ответе
        │
200 {"answer": "...", "sources": [{n, id, doc, title, text, score}], "refused": false}
502 {"error": "..."} — если модель недоступна или вернула ошибку
```

## API

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/health` | `{"status":"ok","documents":N,"chunks":M}` — для healthcheck Docker |
| `POST` | `/api/chat` | см. выше |
| `GET` | `/api/documents` | отсортированный список имён документов |
| `GET` | `/api/documents/{name...}` | `{"name","text"}` — полный текст; имя может содержать `/` (подпапки) |
| `GET` | всё остальное | файл из `STATIC_DIR`, иначе `index.html` (SPA-фолбэк) |

Ошибки всегда JSON вида `{"error": "текст"}`. Запросы к `/api/*` логируются (метод + путь).

## База знаний (`kb.go`)

- **Нарезка.** Строки вида `Статья 5`, `Глава 2`, `Раздел IV` начинают новую «секцию»;
  строки `1.`, `2.3.`, `п. 4` — новый пункт внутри неё. Заголовок фрагмента:
  `Статья 164. Налоговые ставки › п. 1`. Длинные куски режутся по 1500 символов.
- **Токенизация.** Нижний регистр, только буквы/цифры, каждое слово обрезается до 5 символов —
  грубая замена стемминга («ставка/ставке» → «ставк»).
- **BM25.** k1 = 1.5, b = 0.75, IDF в варианте Lucene (`log(1 + (N-df+0.5)/(df+0.5))`) — не уходит в ноль
  на маленьких базах. Возвращаются только фрагменты со score > 0.

## LLM-клиент (`llm/client.go`)

POST `{LLM_BASE_URL}/chat/completions`, заголовок `Authorization: Bearer {LLM_API_KEY}`,
тело `{model, messages, temperature}`. Таймаут — `LLM_TIMEOUT_SEC`. Ошибочный статус возвращается
с первыми 300 символами тела — видно в логах и в `error` ответа API. Ретраев и стриминга нет.

## Настройки (env)

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `ADDR` | `:8000` | адрес сервера |
| `KB_DIR` | `data/kb` | папка базы знаний |
| `STATIC_DIR` | `frontend/dist` | собранный фронтенд |
| `LLM_BASE_URL` | `https://api.deepseek.com/v1` | endpoint модели |
| `LLM_API_KEY` | — | ключ (только в `.env`, не в git) |
| `LLM_MODEL` | `deepseek-v4.1-flash` | имя модели |
| `LLM_TEMPERATURE` | `0.1` | |
| `LLM_TIMEOUT_SEC` | `60` | |
| `TOP_K` | `8` | сколько фрагментов отдавать модели |
| `MIN_SCORE` | `1.0` | порог отказа без LLM — подбирать на тестовых вопросах |

## Запуск и тесты

```bash
cd backend
KB_DIR=../data/kb STATIC_DIR=../frontend/dist LLM_API_KEY=... go run ./cmd/server
go test ./...
go vet ./...
```

Фронтенд в dev-режиме (`cd frontend && npm run dev`, порт 5173) проксирует `/api` на `:8000`.

Тесты сейчас:
- `kb`: находит нужную статью, не находит лишнего, заголовок пункта содержит статью, нарезка длинного текста;
- `assistant` (с поддельной LLM): отказ без вызова модели, в источниках только процитированное,
  поддельные system-сообщения не доходят до модели.

## Чего нет / что брать в работу

Отмечено по приоритету для бэкенда:

1. **Прогон тестовых вопросов организаторов** — CLI или эндпоинт, который гоняет их через `assistant`
   и сохраняет ответы (для сравнения с эталоном и подбора `MIN_SCORE`).
2. **Ретраи и понятные ошибки LLM** — сейчас один запрос, при 429/5xx сразу 502.
3. **Таймауты/контекст** — у `http.Server` задан только `ReadHeaderTimeout`; нет `WriteTimeout`,
   graceful shutdown, ограничения частоты запросов.
4. **Самопроверка ответа** — второй вызов LLM: «все ли утверждения подтверждены фрагментами?»,
   встраивается в `assistant.Answer` после шага 5.
5. **Отдельный ответ «не по теме»** — сейчас на непрофильный вопрос тот же отказ «не найдено».
6. **PDF** — в Go не читается; либо конвертировать заранее, либо добавить библиотеку.
7. **Гибридный поиск** (bge-m3 + реранкер) — зона Левашева; подключается новой реализацией `kb.Searcher`,
   бэкенду нужно будет только передать её в `assistant` в `main.go`.
8. **Синхронизация с `submission/`** — Python-версия для платформы повторяет ту же логику;
   любые правки промпта/порога/нарезки нужно переносить и туда.

Ограничение по проверке: Docker-сборка (`docker compose up --build`) пока не запускалась,
с реальной моделью и базой организаторов бэкенд не прогонялся.
