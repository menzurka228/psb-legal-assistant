# Сабмит для автоматической проверки

Платформа запускает `solution.py` в Docker: на вход `data/questions.csv` (`id,question`) и `data/kb.zip`,
на выходе `submission.csv` (`id,answer`, все поля в кавычках, ответ в одну строку).
Диалоги приходят внутри `question` строками `Пользователь: …` / `Ассистент: …`.

## Как работает `solution.py`

1. **База знаний.** Файлы `документы компании__*` — документы компании, `законы__*` — статьи законов.
   Строки, адресованные ИИ («игнорируй…», «для ИИ-ассистента…»), вырезаются как инъекции
   (в базе есть такая — в служебной записке об архиве).
2. **Паспорта и хронология** (строятся автоматически при загрузке, без ручной разметки):
   - паспорт каждого документа компании: тип, номер, дата, стороны с ИНН, срок действия, период действия
     редакции, что изменяет доп. соглашение и с какого условия, ссылки на другие документы, статус на сегодня;
   - редакции одного документа связываются: у старой появляется «действовала по …», у договора — «изменён: …»;
   - хронология изменений законов из пометок «Пункт 3 изменен с …» (с 2020 г.), с отметкой «вступит в силу в будущем».
   Посмотреть, что получит модель: `DATA_DIR=data python submission/solution.py --show-context "вопрос"`.
3. **Контекст для модели:**
   - документы компании — **целиком** (≈16 тыс. симв.), чтобы модель видела все редакции и доп. соглашения;
   - **перечень всех законов** — чтобы честно говорить, каких норм в базе нет;
   - **законы** — гибридный поиск: BM25 (+ аббревиатуры НДС/НДФЛ/… и юридические термины для бытовых слов:
     «штраф» → «налоговые санкции», «перерабатывать» → «сверхурочная работа») и эмбеддинги `baai/bge-m3`,
     объединение RRF → реранкер → топ-8. Пять сильнейших совпадений сохраняются, а часть оставшихся мест может занять другая статья. К лучшему фрагменту длинной статьи добавляются соседние абзацы, если хватает места в контексте. Явная ссылка в вопросе («ст. 164 НК», «152-ФЗ») гарантирует,
     что статья попадёт в контекст. Короткая статья (до `LAW_FULL_CHARS` симв.) идёт **целиком** — модель видит
     все части и исключения; длинная (ст. 164, 284 НК…) — найденными фрагментами в порядке текста.
4. **Диалог** разбирается в историю сообщений `user/assistant`. Поиск — по текущему вопросу (вес 1) и по нему же
   с предыдущими репликами (вес 0,5): уточнение не теряет тему, а смена темы («А ставка налога на прибыль?») не тонет в старой.
5. **Промпт** (`SYSTEM_PROMPT`): ссылки на пункты, честный отказ, указание на ошибку в вопросе,
   редакция на дату события, похожие контрагенты, законность, защита роли, вопросы не по теме,
   формат «прямой ответ + обоснование, 2–5 предложений», документ называется полностью (вид, номер, контрагент);
   три примера формы ответа на вымышленных документах.
6. **Проверка номеров** (всегда, без лишних вызовов): если в ответе есть номер документа, которого нет ни в базе,
   ни в вопросе (например, «№ П-18/2024»), модель получает одну просьбу исправить ответ.
   **Самопроверка** выполняется после записи всех первичных ответов. По умолчанию (`SELF_CHECK=auto`) сначала проверяются подозрительные ссылки, сложные вопросы и отказы, затем остальные ответы в пределах бюджета. `SELF_CHECK=1` проверяет все ответы при наличии времени, `SELF_CHECK=0` оставляет только проверку подозрительных номеров.
7. Любой сбой эмбеддера/реранкера → BM25; модель: до 5 попыток с паузой (при 429 — растущая или `Retry-After`),
   ошибки запроса 4xx не повторяются; затем заглушка-ответ (прогон не падает).
8. **Подключение к API организаторов**: адрес и ключ платформа передаёт в окружении (`LLM_BASE_URL`, `LLM_API_KEY`
   или `OPENAI_*`); без ключа запросы идут без авторизации. Точные имена моделей не опубликованы — для эмбеддингов
   и реранкера решение само подбирает принятое API имя и запоминает его.
9. **20 минут**: новые вопросы не начинаются за 30 с до бюджета. CSV атомарно записывается после основного прохода и обновляется результатами перепроверки. Логи показывают число технических заглушек и исправлений.
10. Имена файлов в `kb.zip` без флага UTF-8 (архив с Mac/Linux/Windows) декодируются правильно; закон распознаётся
    и по содержимому («Источник: Статья …»).

## Команды

```bash
# офлайн-тесты
python -m pytest submission

# прогон на демо-вопросах + оценка LLM-судьёй по эталону (ключ — только в окружении!)
export LLM_BASE_URL=... LLM_API_KEY=...
python submission/evaluate.py                 # → submission/submission.csv, submission/eval_report.csv
SELF_CHECK=1 python submission/evaluate.py    # то же с самопроверкой

# архив для загрузки на платформу
./submission/make_submission.sh
```

## Настройки (env)

| Переменная | По умолчанию | |
|---|---|---|
| `LLM_MODEL` | `deepseek/deepseek-v4.1-flash` | генерация |
| `EMB_MODEL` | `baai/bge-m3` | эмбеддинги |
| `RERANKER_MODEL` | `qwen/qwen3-reranker-8b` | Qwen3 Reranker 8B (по правилам); если имя не принято — перебираются `Qwen/Qwen3-Reranker-8B`, `qwen3-reranker-8b`… |
| `LAW_TOP_N` / `LAW_CANDIDATES` | 8 / 30 | фрагментов законов в промпт / в реранкер |
| `LAW_FULL_CHARS` / `LAW_CONTEXT_CHARS` | 8000 / 40000 | статья короче — целиком; потолок объёма законов в промпте |
| `LLM_ATTEMPTS` | 5 | попыток вызова модели |
| `SELF_CHECK` | `auto` | перепроверка по приоритету после основного прохода |
| `MAX_WORKERS` | 6 | параллельных вопросов |
| `TIME_BUDGET_SEC` | 1020 (17 мин) | к этому сроку `submission.csv` пишется в любом случае (лимит платформы — 20 мин) |
| `REQUEST_TIMEOUT_SEC` | 90 | таймаут одного запроса к API |
| `TEMPERATURE`, `MAX_TOKENS` | 0.0, 2048 | |
